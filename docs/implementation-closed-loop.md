# 任务交付闭环（对长期任务推荐）

这份说明用于长期固定工作流，目标是减少反复和偏差：**先确认需求契约（Spec），再形成可执行 Plan，再实施**。

在 Codex 中需要完整执行这套标准流程时，直接使用 `agentic-orchestrate-delivery`。本文件保留为面向人的简要说明；Skill 额外固化了主线程职责、角色契约、独立审查、工程验证、用户验收以及文档和 Git 收口。

## 适用场景

- 多模块联动（域模型、数据库、接口、UI、异步任务）
- 有依赖顺序（A/B/C 或多阶段）
- 需要明确验收证据而非“感觉完成”

## 阶段定义（强制顺序）

### 1) Spec（需求定稿）

先把“要做什么”说清楚：

- 目标、边界、非目标
- 业务语义（成功/失败定义）
- 风险边界与失败语义
- 兼容与降级策略
- 验收标准（可观察）

如果存在以下任一项：产品/UX/架构/迁移语义开放 → 先走
`agentic-design-planning`，否则可以直接进入下一步。

### 2) Plan（实施计划）

在 Spec 稳定后，先生成 implementation-ready plan：

- 拆分成 2–6 个可交付任务
- 明确每个任务的 **单一文件边界**
- 记录输入/输出契约（types、schema、接口、持久化）
- 明确依赖顺序（顺序/并行）
- 绑定验收检查命令

建议固定用：

- `agentic-writing-plans`：把 Spec 转为可执行 Plan
- `agentic-subagent-driven-development`：当 Plan 出现“独立可并行写入”且风险可控时，分发并行执行（主线程保持主控）

Plan 仍未确定时不应边写边改；边界不清晰要回到 Plan。

### 3) 实施（Execution）

执行按计划顺序落地，按任务边界逐步验收：

- 每个任务只改负责的文件集合（避免跨任务越权改写）
- 有新决策风险时回写到 Plan 或 Spec
- 变更后立即补对应单元/集成验证
- 完成后更新闭环证据（命令 + 结果摘要）

### 4) 交付闭环（Closure）

- 汇总每项验收证据是否通过
- 标明未解决项与受限项
- 明确下一步执行边界

## 典型任务分层（Plan A / B / C）

当任务天然可分层时，推荐固定命名：

- **Plan A**：基础事实模型与持久化边界（不可变快照、revision、ownership、基础数据）
- **Plan B**：主流程接入（生成、审核、状态流转、主要体验）
- **Plan C**：下游交付（导出、发布、扩展渠道）

Plan A/B/C 之间只允许稳定契约交接，不回退到前序阶段去重建基础真相。

## 模型分工（推荐）

- **Spec + Plan**：用“深度思考”模型（高可解释性、边界推演、依赖分析）
- **执行阶段**：用一般模型执行固定实现（保持速度与可控性）
- 例外：出现架构/语义分歧时，优先回到深度模型，冻结并修订 Spec 或 Plan

## 现场执行记录（可选）

- 当任务复杂度较高、并行任务 > 2、或需长时间追踪时，可在仓库中保留一个简明 `progress.md` / 工作日志
- 内容建议包含：计划来源、文件边界、状态、验收结果、阻塞与风险
